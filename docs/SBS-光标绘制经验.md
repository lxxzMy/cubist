# SBS 输出下的光标绘制：为什么这件事这么复杂

> 背景：程序把桌面画面采集 → 深度推理 → 视差扭曲 → 按 SBS（左右/上下分屏）输出到 3D 显示器。
> SBS 模式下"画面被复制成两半，每半是一只眼"，而 Windows 的真实光标只有**一个**。
> 于是光标必须由程序自己画，而且要画**两份**（每半一份）。本文记录这条链上所有踩过的坑，供他人复用。

---

## 0. 一句话结论

**我们在管线里重新实现了一遍"合成器的光标合成"**，而它必须同时满足：
全局隐藏真光标、实时跟踪形状、正确的 DPI/压缩比、每帧只画一次、每眼各一份、还要和播放器争 Z 序。
Windows 在这五件事上各有一个陷阱，这就是复杂度的全部来源。

---

## 1. 为什么 SBS 必须自绘光标

| 显示模式 | 光标 |
|---|---|
| 行交错（Interleaved） | 系统光标天然正确（一只光标，跨两个眼睛的行），**不要管它** |
| SBS / TAB | 真实光标只有 1 个，而两半都要有各自的一份 → **必须自绘 + 隐藏真光标** |

实测判据：把自绘关掉后，SBS 画面里只剩 1 个光标（在屏幕中间的真实位置），
说明真实光标**不会**被 SBS 复制到两半 —— 它不是"画面的一部分"，是合成器叠加层。

---

## 2. 隐藏真光标：三条路，两条有坑

### 2.1 `ShowCursor(FALSE)` —— 对别的线程无效
- 显示计数是**每线程**的。从后台线程调用返回 `-1`，但 `GetCursorInfo` 仍报 `SHOWING=True`。
- 必须 `AttachThreadInput(本线程, 前台线程)` 之后再调用，才真正隐藏（实测 `SHOWING=False`）。
- 且计数起点不一定是 0，要循环压到真的隐藏（**加次数上限**，恢复时等量加回）。
- **致命副作用**：一旦真隐藏，`GetCursorInfo().hCursor` 变成 **NULL** → 形状信息丢失。

### 2.2 `SetSystemCursor(空白位图)` —— 保住句柄，但管不到应用自定义光标
- 替换 14 个系统光标槽位为透明位图：光标不可见，但 `hCursor` 仍有效 → **可以继续查形状**。
- 技巧：每个槽位的空白位图用不同的**位图宽度**编码槽位序号，之后 `GetIconInfo` 读宽度即可反查"这个位置原本是哪种光标"（箭头/I 型/手型…）。
- **局限**：浏览器/播放器用 `SetCursor(自己的位图)` 设置的光标**完全不经过系统表**，替换无效，仍然可见。

### 2.3 结论
- 想**保住形状**：用 2.2（空白替换），并接受"应用自定义光标盖不住"。
- 想**彻底隐藏**：用 2.1，但代价是拿不到形状。
- 两者不可兼得（这是 Windows 的设计，不是实现问题）。

---

## 3. 形状从哪来：三条来源，各有副作用

| 来源 | 做法 | 陷阱 |
|---|---|---|
| ① 句柄缓存表 | 启动时（隐藏前）缓存 14 个系统光标句柄→位图 | 只能覆盖标准光标 |
| ② `WM_SETCURSOR` 探测 | 给指针下的窗口发 `WM_SETCURSOR`，逼它重新 `SetCursor`，再读句柄 | **会打败播放器的自动隐藏**：播放器藏→我们探测→它又冒出来→循环。必须**只在鼠标移动时探测** |
| ③ 命中测试推断 | `NCHITTEST` 边框→双向箭头、编辑控件→I 型 | 猜的，仅兜底 |

② 的坑实测代价：以 100ms 固定周期探测时，光标"稍长于正常时间才消失"，
因为探测不停把光标唤醒；改成"鼠标移动才探测"后消失时间恢复正常。

---

## 4. 绘制几何：两个必须对齐的量

1. **热点（hotspot）**：必须用 `GetIconInfo` 的 `xHotspot/yHotspot`。提取出来的热点若落在位图正中（如 128×128 的 `(64,64)`），几乎肯定错了，画出来会和真实光标错位几十像素。
2. **压缩比**：SBS 每半是横向（或纵向）**0.5 压缩**的画面，光标必须同样压缩，否则和内容比例不符。
   - Half-SBS：`scale=(0.5, 1.0)`
   - Half-TAB：`scale=(1.0, 0.5)`

---

## 5. 绘制质量：为什么"我们画的丑、系统的漂亮"

根因不是画技，是**缩小采样方式**：

| 路径 | 112px 光标 → 56px 显示 |
|---|---|
| 系统合成器（DWM） | 带过滤的高质量缩放 |
| GL 直接画 0.5 倍，无 mipmap | **漏采样 → 硬锯齿** |
| GL + mipmap 三线性 | 仍只是近似，偏糊 |
| **CPU `cv2.INTER_AREA` 预缩放 → 1:1 画** | **最优**：2:1 时等于两像素精确平均 |

推荐做法（实测最锐）：

```
rgba = cv2.resize(rgba, (w*0.5, h*0.5), interpolation=cv2.INTER_AREA)
hotspot *= 0.5
texture.write(rgba)      # 上传最终尺寸
draw(scale=(1.0, 1.0))   # GL 不再缩放
```

注意：**原生光标不会被 SBS 压缩**，所以它永远比我们的"略锐"；这是比例正确性的代价，不是 bug。

---

## 6. 重复绘制：为什么会看到 4 个光标

SBS 的渲染循环**每帧渲染两遍**（左眼、右眼各一遍）。如果每遍都调光标绘制，
而每次绘制又给两半各画一份 → 2×2 = **4 个**。

历史修复（本仓库 `2d9d6be`）：**每帧只画一次** —— 在其中一遍里画那一对。

要注意后来的一个反模式：
用"时间戳节流（4ms）"代替帧号守卫。GPU 直通路径没有帧号（`frame_id` 恒 None），
所以时间戳看着能用，但语义不对（它按时间而非按帧去重），换帧率/加载抖动时会漏。
正确语义：**每渲染帧一个绘制批次**（用自增的 render 序号）。

```python
if self._cursor_drawn_seq == self._render_seq:   # 同一帧第二遍 → 跳过
    return
self._cursor_drawn_seq = self._render_seq
```

## 7. 还有一个隐藏来源：采集端自己画了光标

全屏输出会切到 `DesktopDuplication`（DXGI），而 **DXGI 的帧里从来不含光标**，
所以采集层往往会"手动把光标合成进画面"（本仓库 `_CursorComposite`）。
这个光标一旦进了画面，**SBS 会把它复制到两半** → 再加上我们自绘的，又是 4 个。

规则：**SBS/全屏输出时，采集端绝不能合成光标**（`if DRAW_CURSOR and not FULLSCREEN_OUTPUT`）。

判别方法（很重要）：
- 多出来的光标**每半各一个** → 它在**采集画面里**（播放器自绘 / 采集端合成）
- 多出来的光标**全屏只有一个** → 它是**真实光标**（应用自定义光标，盖不住）

---

## 8. 显示/隐藏的时机

- ❌ 固定计时器（静止 2 秒隐藏）：用户只是在阅读时也会消失，体验错。
- ✅ 镜像系统状态：空白替换**不会**让 `hCursor` 变 NULL，所以
  `GetCursorInfo().hCursor != NULL` 仍然是"系统是否想显示光标"的有效判据 ——
  播放器空闲隐藏时会调 `ShowCursor(FALSE)`/`SetCursor(NULL)`，此时句柄变 NULL，我们跟着隐藏。
- 若为了彻底隐藏而用了 `ShowCursor(FALSE)`（句柄变 NULL），就只能退回"鼠标移动 + 超时"的启发式。

---

## 9. 与播放器的共存（最容易被忽略的一层）

1. **播放器自绘光标**：部分播放器把光标画进视频像素 → SBS 复制成两份 → 我们的自绘变成多余的一份。
2. **Z 序争抢**：PotPlayer 暂停时会把自身提到 topmost，双方都是 topmost 时"后到者胜" → 它压住覆盖层，
   用户看到播放器画面 + 采集黄框约 1 秒 = "暂停退出 3D"。
   - 修复：渲染循环每帧查 `GetWindow(hwnd, GW_HWNDPREV)`，异进程且非 shell 窗口就
     `SetWindowPos(HWND_TOPMOST, SWP_NOACTIVATE|SWP_NOSIZE|SWP_NOMOVE)` 抢回。
   - **动作不能节流**：节流 200ms 就等于白给 200ms，用户看到的就是"闪一下"。
   - 要排除 shell 窗口（`Shell_TrayWnd/Progman/WorkerW`），它们本来就是 topmost，抢它们没意义。
3. **采集会话重建**：暂停过渡态下 `CreateForWindow` 可能返回 `E_INVALIDARG`，
   旧代码直接清场 = 杀 3D；正确做法是**不清场、保留旧会话下轮重试**（1~3 轮即恢复）。

---

## 10. 为什么必须这么复杂：逐条对照

| 需求 | 为什么简单做法不行 |
|---|---|
| 两半各一个光标 | 真实光标只有一个，且不随 SBS 复制 |
| 隐藏真光标 | `ShowCursor` 是每线程的；`SetSystemCursor` 管不到应用自定义光标 |
| 实时形状（I 型/手型） | 隐藏后拿不到句柄；探测又会破坏播放器的自动隐藏 |
| 清晰的边缘 | 0.5 压缩必须自己做盒式滤波，GL 缩小会混叠 |
| 不能出现 4 个 | SBS 每帧渲染两遍 + 采集端可能也画了一份 |
| 正确的位置 | 热点必须来自真实光标，且要跟着压缩比缩放 |
| 和播放器共存 | 播放器会抢 Z 序、会自绘光标、会改采集可用性 |

**这就是全部复杂度：我们在一个"采集→推理→扭曲→分屏"的管线里，
重新实现了一个合成器级的特性，而它的每一个前置条件在 Windows 上都各有一个坑。**

---

## 11. 落地检查清单

- [ ] 行交错：`CURSOR_MODE=off`，完全交给系统（别画）
- [ ] SBS/TAB：空白替换系统光标表（宽度编码槽位）+ 自绘
- [ ] 自绘入口：每渲染帧只进一次（用 render 序号，不要用时间戳）
- [ ] 每帧内：对每个眼的半屏各画一份（`pts` 列表）
- [ ] 纹理：CPU `INTER_AREA` 预缩放到目标尺寸，`scale=(1,1)` 绘制
- [ ] 热点：来自 `GetIconInfo`，并按压缩比缩放
- [ ] 形状：优先句柄缓存表 → `WM_SETCURSOR`（**仅鼠标移动时**）→ 命中测试兜底
- [ ] 采集端：全屏/SBS 时禁止 `_CursorComposite`
- [ ] 显示判据：`hCursor != NULL`（空白替换不破坏该判据）
- [ ] Z 序：每帧查 `GW_HWNDPREV`，非 shell 异进程立即抢回（不节流）
- [ ] 采集重建：`E_INVALIDARG` 不清场，重试而非杀会话
